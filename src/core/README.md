Pure logic (constraints · generation · validation) with zero runtime dependencies, imported by both the browser and the Worker.

- **It does not build sentences** — violations, steps, explanations and parse errors come back as `CoreMessage` (the discriminated union in `messages.ts`: `code` · `field` · `params`). Sentences are built in `src/messages/`
- String literals in non-test sources contain no Hangul — `no-hangul.test.ts` counts only literal nodes through the TypeScript compiler API (comments are allowed)
- A change that can alter a name, verdict, suggestion or label for the same input bumps `RULES_REVISION` (`revision.ts`) and rewrites `rules-fingerprint.json`. The fingerprint holds a token hash of this folder's non-test sources (except `revision.ts` and `baseline-inputs.ts`), so the revision must be bumped when any logic token changes, even if the output samples stay the same. Changing only comments, whitespace or `displayName` wording does not change the fingerprint
- Every rule states `scope` (where the name must be unique — a key of `SCOPES` in `scopes.ts`), `entity` (the uniqueness class — the provider's type name), `category` (display grouping) and `uniqueness` (`none` is the AWS Name tag). Scope rows carry an official `docUrl` that says "unique within this". The resource tree is built by `buildTree(provider, rules?)` in `tree.ts` from `SCOPES` and `RULES` (`rules` is passed only by the UI's test fixtures) — the tree is never written by hand. Adding a rule or a scope row grows the tree
- Sequence and role are values of an **item**, not of the context (`tokenValues(ctx, rule, { seq, role })` — without them `01` · `sync`, the same as today's output). `generateMany(ctx, provider, selection)` builds a name for every picked item — sequences have two digits (`01`…`99`); rules without input and role rules give one name. The selection first goes through `validateSelection(provider, raw, rules?)` in `selection.ts` (count 1–99 · items ≤ 200 · total names ≤ 200 · no duplicate `type` · count 1 for rules without a sequence · roles only on role rules) — the API, the UI and share links use the same function
- **Role token `tier` and project level** (D60 · D63) — every count rule of the three providers has `tier` right before `seq` (after the kind token: `…-{slug}[-{kind}]-{tier}-{seq}`). It is a protected token (never shortened or dropped) and empty unless an item gives it, so existing names are unchanged. `level: 'project'` drops the `purpose` slot, with `ProjectContext` (no `purpose`) from `parseProjectContext(raw, provider)`. `generateItem(ctx, rule, extra)` builds one item with these values and no conflict check; `generateMany` and `validateSelection` do not read them. `RESERVED_TIERS` (`tier.ts`) lists the words a tier may not be: abbreviations, kind tokens, every environment value and alias the context parser accepts, and region codes
- **Project generation and attachments** (D62 · D69) — `generateProject(selection, provider)` builds one project in a fixed order: every parent (the implicit project ID, project-level items, every service), one conflict pass over all of them, then every requested attachment, then a second conflict pass. Sequence numbers are the slot values (`instances[].seq`) and are never renumbered. Each item has a structural key from `projectItemKey()` — `<level>/<service>/<type>/<tier|->/<seq|role|->`, plus `/<attach>/<seq|->` for an attachment (`service/shop/compute_instance/web/01/data/01`); `generateMany` keeps its own keys. An attachment name is the parent's final name plus `-{attach}[-{seq}]` (`attachName`, `checkName` only, never shortened): too long gives `name.cannot_fit` with `name.parent_name`, and an invalid parent gives an empty name with `name.parent_invalid`. Which parent takes which attachment is data (`wizard/attachments.ts`, `ATTACHMENTS`); `checkAttachments(item, index)` checks the attachment input and returns each problem with its path tail
- **Wizard model** (D64) — `wizard/plan.ts` holds the wizard's input model `WizardPlan` (project values without `purpose`, project-level picks, services with picks; a pick is one rule, with server slots `instances[]` carrying `id` · `seq` · `attach`). `validatePlan(plan)` is the one check for every caller: presets, services (empty · reserved `project` · duplicate after cleaning), tiers (`TIER_PATTERN`, `RESERVED_TIERS`, count rules only), project level, slot ids and numbers, attachments (`checkAttachments`), HA (only a preset with HA data whose effective rule after `serverless` is a VM, at least `minInstances` slots), and the total of names (project ID + project level + parents + attachments ≤ 200). It then runs `validateSelection` once per pick (a one-item list). Every error on an input element carries `path` (`services[1].picks[0].instances[1].attach.data[0]` · `projectPicks[2]` · `services[1]` · `projectPicks`); model-wide errors (`wizard.empty` · `wizard.too_many_names` · `wizard.too_many_services`) have none. `expandPlan(plan)` turns a checked model into the `ProjectSelection` for `generateProject` — slot ids are dropped and preset defaults are never added. Presets are data (`wizard/presets.ts`, `PRESETS`)
- `conflict.ts` catches the same name in the same class (`entity`) within one request. **Every** conflicting item gets `valid:false` and `name.conflict`, and `ManyResult.conflicts` is the summary — exports look at each item's `valid`, so a conflicting name never leaves as valid. One request is treated as one instance of the parent scope (one RG · one project · one VPC). Test-only conflict rules live in `__fixtures__/conflict.ts`
- **The enabled providers are `ENABLED_PROVIDERS` in `types.ts` (`['gcp']` in this release)** (D45). `Provider` and `PROVIDERS` keep all three, and rules, tests and baselines run over all three providers — only what is exposed follows this array
- **For Google Cloud, the catalog overrides abbreviations, `entity`, the region-token kind (`none` · `region`) and the kind table** (D46 · D47). The source is `catalog/*.json` at the repository root; `npm run catalog` writes the generated files `rules/gcp-catalog.ts` and `regions-data.ts` (never edit them by hand), and `applyCatalog(rule)` in `rules/gcp.ts` overrides each rule. Lookups live in `catalog.ts` (`catalogFor` · `rowOf` · `allowedKinds` · `kindToken`)
- **Regions are provider-specific codes** (D49 · D50 revised) — `canonicalRegion(raw, provider)` in `regions.ts` resolves a region or zone name, a code or `global` into `{ region, zone? }`. `parseContext(raw, provider)` takes the provider. Names carry the region code only — `zone` is kept in the context for display and never enters a name, so zonal rules are named like regional ones. A missing required kind gives `name.kind_required` (the name is kept) — on both the `generate` and `generateMany` paths

## 한국어

순수 로직(제약 · 생성 · 검증) — 런타임 의존성 0, 브라우저와 Worker 양쪽에서 import 한다.

- **문장을 만들지 않는다** — 위반 · 단계 · 설명 · 파싱 오류는 `CoreMessage`(`messages.ts` 의 판별 유니언: `code` · `field` · `params`)로 돌려준다. 문장은 `src/messages/` 가 만든다
- 비시험 소스의 문자열 리터럴에 한글이 없다 — `no-hangul.test.ts` 가 TypeScript 컴파일러 API 로 리터럴 노드만 센다(주석은 된다)
- 같은 입력에서 이름 · 판정 · 제안 · 라벨이 바뀔 수 있는 변경은 `RULES_REVISION`(`revision.ts`)을 올리고 `rules-fingerprint.json` 을 다시 쓴다. 지문에는 이 폴더 비시험 소스(`revision.ts` · `baseline-inputs.ts` 제외)의 토큰 해시가 들어 있어, 출력 표본이 같아도 로직 토큰이 하나라도 바뀌면 올려야 한다. 주석 · 공백 · `displayName` 문구만 바꾼 것은 지문을 바꾸지 않는다
- 규칙마다 `scope`(이름이 유일한 범위 — `scopes.ts` 의 `SCOPES` 키) · `entity`(고유성 부류 — CSP 유형 이름) · `category`(표시 분류) · `uniqueness`(`none` 은 AWS Name 태그)를 적는다. 범위 행에는 「이 안에서 유일하다」는 공식 문서 `docUrl` 이 붙는다. 리소스 트리는 `tree.ts` 의 `buildTree(provider, rules?)` 가 `SCOPES` 와 `RULES` 에서 만든다(`rules` 는 화면의 시험 전용 fixture 가 넘긴다) — 트리를 손으로 적지 않는다. 규칙 · 범위는 행을 더하면 트리가 따라 는다
- 순번 · 역할은 문맥이 아니라 **항목**의 값이다(`tokenValues(ctx, rule, { seq, role })` — 없으면 `01` · `sync`, 지금 출력과 같다). `generateMany(ctx, provider, selection)` 이 고른 항목마다 이름을 만든다 — 순번은 두 자리(`01`…`99`), 입력 없는 · 역할 규칙은 하나. 선택은 먼저 `selection.ts` 의 `validateSelection(provider, raw, rules?)` 를 거친다(개수 1~99 · 항목 ≤ 200 · 이름 Σ ≤ 200 · `type` 중복 금지 · 순번 없는 규칙에 개수 1 · 역할은 역할 규칙에만) — API · 화면 · 공유 링크가 같은 함수를 쓴다
- **용도 토큰 `tier` · 프로젝트 수준** (D60 · D63) — 세 CSP 의 count 규칙 전부 `seq` 바로 앞에 `tier` 자리가 있다(종류 토큰 뒤 — `…-{slug}[-{kind}]-{tier}-{seq}`). 보호 토큰이라 줄지도 떼이지도 않고, 항목이 주지 않으면 빈 토큰이라 지금 이름이 그대로다. `level: 'project'` 는 `purpose` 자리를 빼고, 문맥은 `parseProjectContext(raw, provider)` 가 만든 `ProjectContext`(purpose 없음)다. `generateItem(ctx, rule, extra)` 가 이 값으로 항목 하나를 만든다(충돌 검사 없음) — `generateMany` · `validateSelection` 은 이 값을 읽지 않는다. `tier.ts` 의 `RESERVED_TIERS` 는 tier 로 쓸 수 없는 글자(약어 · 종류 토큰 · 문맥 파서가 받는 환경 값과 별칭 전부 · 지역 코드)다
- **프로젝트 생성 · 딸린 것** (D62 · D69) — `generateProject(selection, provider)` 가 프로젝트 하나를 정해진 순서로 만든다: 부모 전부(암묵 프로젝트 ID · 프로젝트 수준 · 모든 서비스) → 전체 충돌 표시 한 번 → 요청된 딸린 것 전부 → 충돌 표시 한 번 더. 순번은 슬롯의 값(`instances[].seq`)이고 다시 매기지 않는다. 항목 키는 `projectItemKey()` 의 구조 키 — `<level>/<service>/<type>/<tier|->/<seq|role|->`, 딸린 것은 뒤에 `/<attach>/<seq|->`(`service/shop/compute_instance/web/01/data/01`) · `generateMany` 의 키는 그대로다. 딸린 이름은 부모의 최종 이름 + `-{attach}[-{seq}]`(`attachName` — `checkName` 만, 줄이지 않는다): 넘치면 `name.cannot_fit` + `name.parent_name`, 부모가 무효면 빈 이름 + `name.parent_invalid`. 어느 부모에 무엇이 붙는지는 데이터(`wizard/attachments.ts` 의 `ATTACHMENTS`)이고, `checkAttachments(item, index)` 가 딸린 것 입력을 검사해 문제마다 위치 꼬리와 함께 돌려준다
- **마법사 모델** (D64) — `wizard/plan.ts` 의 `WizardPlan` 이 마법사의 입력 모델이다(purpose 없는 프로젝트 값 · 프로젝트 수준 pick · 서비스와 그 pick. pick 하나 = 규칙 하나, 서버 슬롯 `instances[]` 는 `id` · `seq` · `attach`). `validatePlan(plan)` 이 모든 호출자의 검사 하나다: 프리셋 · 서비스(빈 값 · 예약 `project` · 정제 뒤 중복) · tier(`TIER_PATTERN` · `RESERVED_TIERS` · count 규칙에만) · 프로젝트 수준 · 슬롯 id 와 순번 · 딸린 것(`checkAttachments`) · HA(HA 데이터가 있는 프리셋이고 `serverless` 를 푼 유효 규칙이 VM 일 때만 · 슬롯 `minInstances` 이상) · 이름 총합(프로젝트 ID + 프로젝트 수준 + 부모 + 딸린 것 ≤ 200). 그 뒤 pick 마다 `validateSelection` 을 한 번(한 항목짜리 목록) 부른다. 입력 요소에 걸린 오류에는 `path`(`services[1].picks[0].instances[1].attach.data[0]` · `projectPicks[2]` · `services[1]` · `projectPicks`)가 붙고, 모델 전체 오류(`wizard.empty` · `wizard.too_many_names` · `wizard.too_many_services`)에는 없다. `expandPlan(plan)` 이 검사를 지난 모델을 `generateProject` 의 `ProjectSelection` 으로 펼친다 — 슬롯 id 는 싣지 않고 프리셋 기본값은 넣지 않는다. 프리셋은 데이터다(`wizard/presets.ts` 의 `PRESETS`)
- 같은 요청 안에서 같은 부류(`entity`)의 같은 이름은 `conflict.ts` 가 잡는다. 충돌한 **항목마다** `valid:false` 와 `name.conflict` 가 붙고 `ManyResult.conflicts` 는 그 요약이다 — 내보내기가 항목의 `valid` 를 보므로 충돌한 이름이 유효로 나가지 않는다. 한 요청은 부모 범위의 한 인스턴스(한 RG · 한 프로젝트 · 한 VPC)로 본다. 시험 전용 충돌 규칙은 `__fixtures__/conflict.ts`
- **켜진 CSP 는 `types.ts` 의 `ENABLED_PROVIDERS`(이번 릴리스는 `['gcp']`)다** (D45). `Provider` · `PROVIDERS` 는 셋 그대로이고 규칙 · 시험 · 기준선은 세 CSP 를 다 돈다 — 노출만 이 배열을 따른다
- **GCP 의 약어 · `entity` · 지역 토큰 종류(`none` · `region`) · 종류 표는 catalog 가 덮는다** (D46 · D47). 정본은 저장소 뿌리의 `catalog/*.json`, `npm run catalog` 가 생성 파일 `rules/gcp-catalog.ts` · `regions-data.ts` 를 쓰고(손으로 고치지 않는다), `rules/gcp.ts` 의 `applyCatalog(rule)` 가 규칙마다 덮는다. 조회 함수는 `catalog.ts`(`catalogFor` · `rowOf` · `allowedKinds` · `kindToken`)
- **지역은 CSP 별 코드다** (D49 · D50 revised) — `regions.ts` 의 `canonicalRegion(raw, provider)` 가 리전 · 존 이름 · 코드 · `global` 을 `{ region, zone? }` 로 푼다. `parseContext(raw, provider)` 는 provider 를 받는다. 이름에는 리전 코드만 든다 — `zone` 은 문맥에 표시용으로 남고 이름에 들지 않아 존 규칙도 리전 규칙처럼 이름이 난다. 필수 종류가 없으면 `name.kind_required`(이름은 둔다) — `generate` · `generateMany` 두 경로 모두
