# Rule verification against official documentation

This document records how the hand-written naming rules were checked against the cloud provider's official documentation: the 36 hand-written core rules (`AWS_HAND_RULES`, `GCP_HAND_RULES` and `AZURE_HAND_RULES` in `src/core/rules/{aws,gcp,azure}.ts` — 11 AWS, 10 Google Cloud and 15 Azure; 24 checked on 2026-09-28, plus 11 added on 2026-10-06 — see "Rules added on 2026-10-06" below — plus `gcp.project_name` added on 2026-10-12), the Google Cloud rules added by hand later (the dated sections below), and the 3 entries of `LABEL_LIMITS` in `src/core/constraints.ts`. `RULES` in `src/core/constraints.ts` is the merged table of every provider: these hand-written rules plus the generated `*-intake.ts` rows and the hand-added `*-manual.ts` rows of `src/core/rules/`. On 2026-09-28 each `docUrl` was fetched with `curl -sL`, the HTML tags were stripped, the relevant paragraph was located, and each anchor was confirmed against an `id` in the fetched HTML.

## How to read the tables

The four columns are ⑴ length, ⑵ allowed characters / pattern, ⑶ start / end, ⑷ reserved words / forbidden prefixes and suffixes.

| Verdict | Meaning |
|---|---|
| Match | The code value is the same as the document |
| Mismatch → fixed | The code differed from the document and was corrected. Recorded in [decisions.md](decisions.md) |
| Conservative | The code is stricter than the document. It may reject a valid name, but it never reports an invalid name as valid — kept as is and recorded in [decisions.md](decisions.md) |
| Not applicable | The document has no rule of that kind, and the code has none either |

**Evidence other than a documentation sentence (D80).** Every number and character set comes from an official page (`docUrl`), with two exceptions for limits that no page states. A rule may then cite ⑴ `sdk` — validation code that Google publishes in its own client (package, version, file, function, and the regular expression or message word for word), or ⑵ `api_error` — the server's response to real requests against a real project (method and request path, date, and the response text word for word; the project ID is written `<project>`). Such a rule keeps its `docUrl` pointing at the how-to page, lists the sources in its `evidence` field, and carries `note.observed_server_rule`. When the SDK and the server disagree, the narrower of the two is used and the difference is written here. These rules are listed in "Rules added on 2026-10-12 from observed server rules" below.

Quotations here and in code comments copy the source word for word, typos included — for example the Compute Engine discovery document's `comply withRFC1035` (no space). Search for the source's spelling, not a corrected one.

**Summary** — rules without a documented source: **0** (no rule removed) · value fixes: **3** · `docUrl` fixes: **4** (plus anchor and domain cleanup) · conservative limits kept: **4**. On 2026-09-28 **3 more conservative limits were added** (GCS consecutive dots `..` forbidden · Azure resource group rejects characters above U+FFFF · Azure VM rejects all dots — rationale in [decisions.md](decisions.md)).

- **BigQuery table — characters and bytes.** The REST reference counts 1,024 characters, the guide 1,024 UTF-8 bytes. The engine counts characters, so the rule takes only the ASCII members of the five categories (letters, digits, `_`, `-`, space), where one character is one byte; a name such as `étudiant-01`, valid on BigQuery, is reported invalid. `\p{M}` would also admit default-ignorable marks (U+034F, U+FE00–FE0F) that every rule rejects. A space is accepted only inside the name: the documents do not forbid a leading, trailing or space-only name, but the rule rejects them conservatively (D20). The guide adds "Some table names and table name prefixes are reserved" without a list, so nothing is encoded for it; the prefixes `_TABLE_`, `_FILE_`, `_PARTITION` and the like are listed for column names in the schema guide, not for tables. A view is created with `tables.insert` and takes the same `tableId`. Generated names are joined with underscores like the dataset (`billing_shop_prod_tbl_01`), so a query names the table without quotes.
- **Logging.** The log bucket's uniqueness scope is not stated; the IDs `_Default` and `_Required` that Logging creates start with `_` and are already rejected. Sinks of organizations, folders and billing accounts use the same identifier rule but are not covered (project-level resources only). Metrics may contain `/` after the first character; the document says `/` "denotes a hierarchy of name pieces" but does not forbid a trailing or doubled `/`, so the rule rejects both conservatively (D20, `note.narrower_source_used`) and generated names never contain `/`. Neither the bucket nor the metric has a uniqueness sentence (only the resource-name format), so both carry `note.scope_unconfirmed`. Log buckets accept `global`, single regions and the `eu` and `us` multi-regions (region-support page).
- **Tags — REST against the guide.** The REST reference allows ASCII letters, digits, `-`, `_` and `.` with an alphanumeric at both ends; the guide allows any UTF-8 character except `'`, `"`, `\` and `/`, and for keys states no first or last character. Both are official; the rule takes the REST form. Only keys created under a project are covered; an organization key is unique in the organization's namespace and is not covered by these rules.
- **Network firewall policy.** The discovery document's `FirewallPolicy.name` says "Name of the resource" only, and its RFC 1035 sentences for `shortName` and `displayName` say "This field is not applicable to network firewall policies". The rule takes the general Compute Engine format instead, which applies "unless specified differently in the documentation for creating that resource"; the insert reference and `gcloud compute network-firewall-policies create` state nothing different. The hierarchical policy of an organization or folder stays held.
